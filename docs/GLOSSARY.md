## 1. 한 장 요약 — 이 프로젝트가 하는 일

리눅스에서 프로그램이 뭔가를 하려면 **커널**에게 부탁해야 합니다 (파일 열기, 네트워크 연결 등).
이 부탁을 **syscall**이라고 합니다. **eBPF**는 이 부탁이 오고 갈 때 커널 안에서 엿들을 수 있게
해주는 기능입니다. Ferrisentry는 컨테이너 안에서 일어나는 수상한 부탁(리버스쉘 실행, 권한 상승,
민감 파일 쓰기 등)을 엿듣고 알려주는 프로그램입니다.

```
컨테이너 안의 프로그램 ──syscall──▶ 커널 ──▶ (eBPF가 엿들음) ──▶ 우리 프로그램 ──▶ 알림
```

## 2. 리눅스 기초

| 용어 | 뜻 |
|---|---|
| **커널 (kernel)** | 운영체제의 핵심. 하드웨어와 프로그램 사이에서 모든 요청을 처리하는 층. 커널 안에서 돌아가는 코드는 권한이 매우 높아서, 잘못 만들면 시스템 전체가 멈춘다 |
| **유저스페이스 (userspace)** | 커널 바깥, 평범한 프로그램들이 도는 영역. 우리가 만드는 에이전트 본체가 여기서 돈다 |
| **syscall (시스템 콜)** | 프로그램이 커널에게 하는 요청. "이 파일 열어줘", "이 주소로 접속해줘" 같은 것. 프로그램이 할 수 있는 모든 의미 있는 행동은 결국 syscall로 나타난다 → 그래서 syscall을 보면 행동을 알 수 있다 |
| **execve** | "이 프로그램을 실행해줘" syscall. 공격자가 쉘(`/bin/sh`)을 띄우는 것도 여기 잡힌다 |
| **openat** | "이 파일을 열어줘" syscall. 민감한 파일 변조를 잡는 데 쓴다. 매우 자주 호출된다 (프로그램 하나 켜는 데 수백 번) |
| **connect** | "이 주소로 접속해줘" syscall. 공격자가 외부 서버로 연결하는 걸 잡는 데 쓴다 |
| **setuid** | "내 권한을 이 사용자로 바꿔줘" syscall. `setuid(0)`은 관리자(root) 권한을 요구하는 것 |
| **PID** | 프로세스 번호. 실행 중인 프로그램 하나하나에 붙는 번호 |
| **PPID** | 부모 프로세스 번호. "누가 이 프로그램을 띄웠나"를 알려준다. 웹서버가 갑자기 쉘을 띄웠다 같은 걸 잡는 핵심 정보 |
| **TGID** | 스레드 그룹 ID. 커널 내부에서는 우리가 보통 "PID"라고 부르는 값이 TGID다. eBPF의 `bpf_get_current_pid_tgid()`는 두 값을 한 숫자에 담아서 주므로, 상위 32비트를 꺼내 써야 한다 |
| **comm** | 프로세스 이름 (예: `bash`, `nginx`). 커널이 16바이트로 잘라서 보관한다 → 그래서 우리 구조체도 `[u8; 16]` |
| **uid** | 사용자 번호. `0`이 root(관리자) |
| **root** | 관리자 계정. 뭐든 할 수 있는 권한 |
| **sudo** | 일시적으로 관리자 권한으로 명령을 실행하는 도구. eBPF 프로그램을 커널에 올리려면 권한이 필요해서 계속 등장한다 |
| **inode** | 파일/디렉터리에 붙은 고유 번호. cgroup 번호를 디렉터리로 되찾을 때 쓴다 |

## 3. eBPF

| 용어 | 뜻 |
|---|---|
| **eBPF** | 커널 안에서 돌아가는 작은 프로그램을 안전하게 끼워 넣는 기능. 커널 소스를 고치거나 모듈을 만들지 않고도 커널 내부 동작을 관찰할 수 있다. 이 프로젝트의 핵심 기술 |
| **probe** | 커널의 특정 지점에 "이 일이 생기면 알려줘"라고 붙여두는 감시 지점. 이 프로젝트는 syscall마다 probe를 하나씩 붙인다 |
| **tracepoint** | 커널 개발자들이 미리 만들어 둔 공식 관찰 지점. 커널 버전이 바뀌어도 잘 안 깨져서 kprobe보다 안전하다. 이 프로젝트는 주로 이걸 쓴다 |
| **kprobe** | 커널 함수 아무 곳에나 붙일 수 있는 감시 지점. 자유롭지만 커널 내부 함수 이름/구조에 의존해서 버전이 바뀌면 깨질 수 있다 |
| **verifier (검증기)** | eBPF 프로그램을 커널에 올릴 때 "이 코드가 커널을 망가뜨리지 않는지" 검사하는 커널 기능. 무한 루프, 잘못된 메모리 접근 등을 거부한다. 거부당하면 프로그램이 아예 안 올라간다 |
| **BPF map** | 커널 쪽 eBPF 코드와 유저스페이스 프로그램이 데이터를 주고받는 공용 저장소. 여러 종류가 있다 |
| **ring buffer (링 버퍼)** | map의 한 종류. 커널이 쓰고 유저스페이스가 읽는 한 방향 큐. 꽉 차면 새 이벤트가 버려진다 → 그래서 유실 수를 세는 코드가 필요하다. 커널 5.8 이상 필요 |
| **PerCpuArray** | map의 한 종류. CPU 코어마다 따로 칸을 두는 배열. 여러 코어가 동시에 더해도 충돌이 없어서 카운터에 적합하다. 읽을 때는 코어별 값을 다 합친다 |
| **BTF (BPF Type Format)** | 커널이 자기 내부 구조체 모양을 스스로 설명해 둔 정보. `/sys/kernel/btf/vmlinux`에 있다. 이게 있으면 커널 구조체(`task_struct` 등)를 코드에서 안전하게 읽을 수 있다 |
| **vmlinux** | 커널 본체(이미지). BTF 정보를 꺼낼 출처로 문서에 등장한다 |
| **task_struct** | 커널이 프로세스 하나를 표현하는 구조체. 부모 PID를 얻으려면 여기서 `real_parent`를 따라가야 한다 |
| **helper 함수** | eBPF 코드가 쓸 수 있도록 커널이 제공하는 함수들 (`bpf_get_current_pid_tgid`, `bpf_probe_read_user` 등). eBPF는 아무 커널 함수나 호출할 수 없고 이 목록만 쓸 수 있다 |
| **CAP_BPF / CAP_SYS_ADMIN** | eBPF 프로그램을 올릴 때 필요한 리눅스 권한 조각(capability). "root 전체 권한" 대신 필요한 조각만 주는 것이 최소 권한 원칙 |
| **bpf-linker** | Rust 코드를 eBPF 바이트코드로 만들 때 필요한 링커. Aya 개발에 반드시 설치해야 한다 |

## 4. Rust / 빌드 도구

| 용어 | 뜻 |
|---|---|
| **Rust** | 이 프로젝트의 언어. 메모리 안전성을 컴파일 시점에 보장해서, 커널에 올라가는 코드를 쓰기에 적합하다 |
| **Aya** | Rust로 eBPF를 작성·로드하는 라이브러리. 커널 쪽(`aya-ebpf`)과 유저스페이스 쪽(`aya`)이 쌍으로 있다 |
| **aya-template** | Aya 프로젝트 기본 골격을 만들어주는 템플릿. Phase 0에서 이걸로 워크스페이스를 만들었다 |
| **aya-tool** | 커널 BTF 정보로 Rust 바인딩(구조체 정의)을 생성해주는 도구. 부모 PID를 읽을 때 필요하다 |
| **crate** | Rust의 패키지/모듈 단위. 이 프로젝트는 3개를 쓴다 |
| **workspace** | 여러 crate를 한 리포지토리에서 함께 빌드하는 Cargo 구성 |
| **`ferrisentry-common`** | 커널과 유저스페이스가 **똑같이** 쓰는 데이터 구조 정의 crate |
| **`ferrisentry-ebpf`** | 커널에 올라가는 코드 crate |
| **`ferrisentry`** | 유저스페이스 에이전트 crate (실행 파일) |
| **cargo** | Rust의 빌드/패키지 도구 |
| **nightly** | Rust의 실험 기능이 포함된 최신 버전 채널. eBPF 빌드에 필요하다 |
| **`no_std`** | 표준 라이브러리 없이 컴파일하는 모드. 커널 안에서는 표준 라이브러리를 쓸 수 없어서 eBPF 코드는 반드시 이 모드다 |
| **`repr(C)`** | 구조체를 C 언어와 같은 메모리 배치로 고정하는 표시. 커널과 유저스페이스가 같은 바이트를 같은 뜻으로 읽게 하려면 필수 |
| **ABI** | 두 코드가 데이터를 주고받을 때 합의한 바이트 배치 규칙. 한쪽만 구조체를 바꾸면 깨진다 → 그래서 크기를 검사하는 테스트를 둔다 |
| **Pod (Rust의 `aya::Pod`)** | "이 구조체는 그냥 바이트 덩어리로 안전하게 복사해도 된다"는 표시. ⚠️ Kubernetes의 Pod와 전혀 다른 말이다 |
| **tokio** | Rust 비동기 실행 라이브러리. 여러 일(이벤트 읽기, 종료 신호 감지)을 동시에 기다리는 데 쓴다 |
| **폴링 (polling)** | "새 데이터 있나?" 하고 주기적으로 들여다보는 방식. 지금은 50ms마다 링 버퍼를 확인한다 |

## 5. 컨테이너 / Kubernetes

| 용어 | 뜻 |
|---|---|
| **컨테이너** | 프로그램을 격리된 환경에 담아 실행하는 방식. 격리는 리눅스 커널 기능(namespace, cgroup)으로 만들어진다 → **커널에서 보면 결국 그냥 프로세스다.** 그래서 eBPF로 들여다볼 수 있다 |
| **cgroup** | 프로세스를 묶어서 자원(CPU, 메모리)을 제한하는 커널 기능. 컨테이너 하나가 cgroup 하나에 대응돼서, "어느 컨테이너의 일인가"를 알아내는 단서가 된다 |
| **cgroup v2** | cgroup의 2세대 방식. 최근 리눅스 기본값. 이 프로젝트의 검증 환경도 v2 |
| **cgroup ID** | cgroup을 가리키는 숫자. eBPF에서 바로 얻을 수 있다. [추정] cgroup v2에서는 이 값이 cgroup 디렉터리의 inode 번호와 같아서, `/sys/fs/cgroup`을 훑어 경로를 되찾을 수 있다 |
| **컨테이너 ID** | 컨테이너마다 붙는 64자 16진수 식별자. cgroup 경로 안에 들어 있는 경우가 많아서 거기서 뽑아낼 수 있다 |
| **Kubernetes (K8s)** | 컨테이너를 여러 서버에 걸쳐 자동으로 배치·관리하는 플랫폼 |
| **Pod (K8s)** | Kubernetes가 다루는 배포 단위. 컨테이너 한 개 이상의 묶음. ⚠️ Rust의 `Pod`와 다른 말 |
| **네임스페이스 (K8s namespace)** | Kubernetes 안에서 자원을 논리적으로 구분하는 칸. ⚠️ 리눅스 커널의 namespace(격리 기능)와 이름만 같고 다른 개념 |
| **노드 (node)** | Kubernetes 클러스터를 구성하는 서버 한 대 |
| **DaemonSet** | "모든 노드에 하나씩" 배포하는 Kubernetes 방식. 감시 에이전트는 모든 노드에 있어야 하므로 이걸 쓴다 |
| **Deployment** | 원하는 개수만큼 복제해서 배포하는 Kubernetes 방식. 중앙 수집기(Collector)에 쓴다 |
| **CRD (Custom Resource Definition)** | Kubernetes에 내가 만든 자원 종류를 추가하는 기능. 탐지 정책을 Kubernetes 자원처럼 관리하려고 쓴다 (Phase 4) |
| **Helm** | Kubernetes 배포 설정을 패키지로 묶어 관리하는 도구 |
| **CRI (Container Runtime Interface)** | Kubernetes와 컨테이너 런타임 사이의 규격. 컨테이너 ID로 "어느 Pod, 어느 이미지인지" 물어보는 데 쓴다 |
| **containerd** | 대표적인 컨테이너 런타임 |
| **kind** | 도커 컨테이너 안에 Kubernetes 클러스터를 만들어주는 테스트 도구 (Kubernetes IN Docker). 노드가 호스트 커널을 공유하므로 eBPF 테스트가 가능하다 |
| **kubectl** | Kubernetes를 조작하는 명령줄 도구 |
| **매니페스트 (manifest)** | Kubernetes에 "이렇게 배포해줘"라고 적어 주는 YAML 파일 |

## 6. 보안 용어

| 용어 | 뜻 |
|---|---|
| **런타임 보안** | 프로그램이 **실제로 돌아가는 동안** 수상한 행동을 잡는 방식. 미리 이미지를 검사하는 방식(정적 스캔)과 대비된다. 이 프로젝트가 속한 분야 |
| **Falco / Tetragon** | 같은 분야의 대표적인 오픈소스 도구. Falco는 CNCF 프로젝트, Tetragon은 Cilium 쪽 프로젝트 |
| **룰 엔진 (rule engine)** | "이런 이벤트가 오면 위험이라고 판단한다"는 규칙을 적용하는 부분. 이 프로젝트는 YAML로 규칙을 적는다 (Phase 2) |
| **리버스쉘 (reverse shell)** | 침입자가 피해 서버에서 **바깥쪽으로** 연결을 만들어 원격 조작 창구를 여는 기법. 방화벽이 보통 들어오는 연결만 막기 때문에 쓰인다. 탐지 1순위 |
| **권한 상승 (privilege escalation)** | 일반 권한으로 침입한 뒤 관리자 권한을 얻으려는 시도. `setuid(0)`이 흔한 흔적 |
| **크립토마이너 (cryptominer)** | 침입 후 서버 자원으로 암호화폐를 채굴하는 악성 프로그램 |
| **오탐 (false positive)** | 정상 행동을 위험이라고 잘못 알리는 것. 너무 많으면 사람이 알림을 무시하게 돼서, 탐지 못 하는 것만큼 나쁘다 |
| **미탐 (false negative)** | 실제 공격을 놓치는 것 |
| **탐지율** | 정해둔 공격 시나리오 중 실제로 잡아낸 비율. 이 프로젝트는 공격 시뮬레이션 3종 전부 잡는 것을 MVP 기준으로 삼는다 |
| **공격 시뮬레이션** | 실제 공격 수법을 일부러 재현해 보는 테스트. 탐지가 되는지 확인하는 유일한 현실적 방법이고, 포트폴리오 데모 자료로도 쓴다 |
| **위협 모델 (threat model)** | "누가, 어떻게 공격할 수 있는가"를 정리한 문서. 이 프로젝트는 **감시 도구 자신이 높은 권한으로 도는 공격 표면**이라는 점까지 문서화하는 것을 어필 포인트로 둔다 |
| **최소 권한 원칙** | 꼭 필요한 권한만 주는 원칙. 에이전트에 root 전부가 아니라 필요한 capability만 주는 식 |
| **seccomp** | 프로세스가 쓸 수 있는 syscall 종류를 제한하는 커널 기능. 에이전트 자신을 보호하는 데 쓴다 |
| **SOAR** | Security Orchestration, Automation and Response. 탐지된 사건에 **자동으로 대응**하는 체계 (예: 해당 Pod 격리, 티켓 생성). 이 프로젝트는 n8n으로 대신한다 |
| **n8n** | 작업 자동화 도구. 알림을 받아서 대응 흐름을 만드는 데 쓸 예정 (Phase 4, 선택) |
| **Webhook** | "사건이 생기면 이 URL로 알려줘"라는 방식의 알림 연동 |
| **gRPC** | 프로그램끼리 통신하는 규격. 노드 에이전트 → 중앙 Collector 통신에 쓸 예정 |

## 7. 이 프로젝트 문서에서 쓰는 말

| 용어 | 뜻 |
|---|---|
| **spec (설계 문서)** | 무엇을 왜 만드는지 정한 문서. [여기](superpowers/specs/2026-09-22-ferrisentry-design.md) |
| **기획서** | 목표, MVP, 로드맵, 리스크를 정리한 문서. [여기](../PLANNING.md) |
| **plan** | 한 Phase를 어떤 순서로 어떻게 구현할지 Task 단위로 쪼갠 실행 문서. Phase를 시작할 때마다 새로 쓴다 |
| **Phase (단계)** | 로드맵을 쪼갠 구현 단계. Phase 0(기반) → 1(핵심 probe) → … → 6(마무리) |
| **Task** | plan 안의 작업 단위. 하나 끝날 때마다 커밋하고 PROGRESS를 갱신한다 |
| **MVP** | Minimum Viable Product. "이것만 되면 쓸 만하다"는 최소 완성 범위. 이 프로젝트에서는 **kind 클러스터에서 공격 3종을 탐지해 알림을 보내는 것**까지 ([기획서 4장](../PLANNING.md#4-mvp)) |
| **PROGRESS** | 진행 현황 문서. 할 일 / 작업 순서(✅🔄⬜) / 완료한 일. [여기](../PROGRESS.md) |
| **완료 기준** | 그 Phase가 끝났다고 말할 수 있는 조건 목록. plan 맨 끝에 있다 |
| **ponytail 주석** | 코드에 일부러 단순하게 처리한 곳과 그 한계를 적어 둔 주석. "나중에 이게 문제가 되면 이렇게 바꿔라"를 남겨 둔 것 |

## 8. 개발 환경

| 용어 | 뜻 |
|---|---|
| **WSL2** | Windows 안에서 진짜 리눅스 커널을 돌리는 기능. eBPF는 리눅스 커널 기능이라 Windows에서 직접 빌드할 수 없어서 반드시 이 안에서 작업한다 |
| **DrvFs / `/mnt/d`** | WSL이 Windows 드라이브(D:)를 리눅스 쪽에 붙여주는 방식과 그 경로. 편하지만 파일 접근이 느려서 빌드가 느리다 |
| **LF / CRLF** | 줄바꿈 문자. 리눅스는 LF, Windows는 CRLF를 쓴다. 셸 스크립트가 CRLF로 저장되면 리눅스에서 실행이 안 돼서, `.gitattributes`로 LF로 고정해 뒀다 |
| **git worktree** | 같은 리포지토리를 여러 폴더에 동시에 펼쳐 쓰는 git 기능. 브랜치 작업용으로 썼고 Phase 0 병합 후 정리했다 |
| **revert** | 이전 커밋의 변경을 되돌리는 새 커밋을 만드는 것. 히스토리를 지우지 않아서, 되돌린 것을 다시 되돌릴 수도 있다 (Phase 0 코드가 실제로 그렇게 복구됐다) |
| **force-push** | 원격 저장소의 히스토리를 로컬 것으로 강제 교체하는 것. 되돌리기 어려우니 주의해서 쓴다 |
| **upstream** | 로컬 브랜치가 따라가는 원격 브랜치 |
| **통합 테스트 (integration test)** | 커널에 실제로 프로그램을 올려서 동작을 확인하는 테스트. `tests/`에 있다. 커널 연동 부분은 유닛 테스트로 검증할 수 없어서 이게 유일한 검증 수단이다 |
| **유닛 테스트 (unit test)** | 커널 없이 함수 단위로 검증하는 테스트. 출력 포맷, 구조체 크기, 경로 파싱 같은 순수 로직에 붙인다 |
